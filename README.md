# Build-and-Find

**Can agents build code other agents can understand?** A benchmark for
artifact-evidenced intent recovery and agent-facing builder artifact quality.

See `paper/neurips2026_eandd/main.tex` and
`experiments/eandd_final_2026/SPEC.md` for the reported methodology and frozen
experiment contract.

## Reviewer quickstart

To inspect the released benchmark without rerunning paid model calls:

```bash
uv sync --extra dev --extra paper
make reviewer-check-fast
make paper
```

The released records already contain the canonical build/find runs used in the
paper. Reproducing model interactions requires access to the listed vendor
CLIs/models and may not be bit-identical because closed models and hosted APIs
can drift. The deterministic analysis can be rerun from `runs_release/`; use
`make reviewer-check` for the slower full local test suite.

## Architecture

```
src/bnf/
├── schema/      BuildTaskSpec, FindQuestion, BuildRun, FindRun (pydantic + YAML)
├── prompts/     Deterministic builder & finder prompt rendering
├── runners/     AgentAdapter protocol + codex, claude-code adapters
├── build/       Sandbox, runner, cargo-based compile probe
├── find/        Runner + exact-match scorer; finder writes find_answers.json
├── analysis/    Builder × Finder matrix, bootstrap CI, CSV/JSON/Markdown
└── cli.py       bnf CLI

benchmarks/
├── specs/              2 final-study build-from-scratch task specs
└── questions/          2 final-study Find question banks, spec-traceable
```

For routine future builder or harness comparisons, use the scripted v1 core
finder panel instead of rerunning every calibrated finder:

- Default core finders: `claude_code_sonnet_4_6_low`,
  `claude_code_sonnet_4_6_high`
- Prior-stress audit finder: `claude_code_mimo_v2_5_pro_low`

The selection is regenerated by `scripts/select_eandd_core_finders.py` and
recorded under `runs_release/reports/eandd_final/core_finder_selection/`. The
default panel is intentionally smaller than the top formal-accuracy set because
some high-accuracy finders have saturated question-only controls on this task
pack.

## Benchmark content

| task_id                    | family                | #FR | #SR | #ER | #MCQ | scale    |
|----------------------------|-----------------------|-----|-----|-----|------|----------|
| `scratch_minidb`           | build_from_scratch    | 17  | 12  | 0   | 15   | 10k+ LOC |
| `scratch_nanoweb`          | build_from_scratch    | 15  | 11  | 0   | 15   | 10k+ LOC |

- **`scratch_minidb`**: an embeddable SQL-subset RDBMS — lexer, parser,
  planner, Volcano-style executor, page-based storage + WAL, transaction
  manager, REPL / batch modes.
- **`scratch_nanoweb`**: an HTTP/1.1 web framework — own HTTP parser, trie
  router, middleware stack, rustls-gated TLS, Prometheus metrics, template
  engine, graceful shutdown.

## Methodology guard-rails

- Builder prompts never contain canonical intention strings or requirement
  IDs; leaking them would trivialise the Find phase.
- The **finder is not told that a spec exists** — it is only given a
  codebase and multiple-choice questions, and picks the option that best
  fits the code. Benchmark ground truth is server-side.
- **Answers are written to a file** (`find_answers.json`) in the finder's
  workspace, not parsed from stdout. This avoids fragile CLI parsing.
- Every Find question carries a `source_trace` back to a spec intention;
  `bnf specs validate` enforces the chain.
- Option order is reordered per-run with a seeded shuffle to neutralise
  position bias (`FindQuestion.shuffled`).
- Each run records a `RunManifest` with `(spec_hash, prompt_hash,
  agent.model_id, seed, trial_id, env_hash)` for reproducibility.
- Build-phase validation is a **compile probe only** (`cargo build
  --release`) — correctness is not fully judged at Build time. The submitted
  primary analysis uses compile-passing artifacts; compile-failed and empty
  artifacts remain in the release as validity-stress diagnostics.
- The released task pack is **high-prior**: accuracy is interpreted as a
  validity gate and calibration signal, while conditional inspection effort is
  an agent-facing proxy for builder artifact quality only after recovery and
  stability gates.
- Builder-finder affinity is a panel-local diagnostic for interaction effects,
  not a universal model-family ranking.
- Metrics use **bytes exchanged with the model** (UTF-8), not tokens, to
  remain model-agnostic.

## Prerequisites

Before running anything, make sure:

- The `codex` and `claude` CLIs are on `PATH` and already logged in (`codex login` / `claude login`). The harness drives both CLIs as subprocesses and does not own their sessions, so any agent whose CLI is unauthenticated will fail.
- To run MiMo (`claude_code_mimo_*` adapters), provide a Bearer token in the `MIMO_API_KEY` environment variable. Other third-party Anthropic-compatible providers use the same mechanism — the adapter specifies which env var to read; see `src/bnf/runners/registry.py`.
- Third-party provider endpoints are adapter configuration, not part of the deterministic release analysis. The reported records can be audited without live provider access.
- To compile the paper, install a TeX distribution that provides `pdflatex`
  and `bibtex`. If your TeX distribution requires a different BibTeX binary,
  pass it explicitly, for example `make paper BIBTEX=bibtex8`. The
  analysis-only checks do not require TeX.

## Quickstart

```bash
uv sync

# Inspect the benchmark
uv run bnf agents list
uv run bnf specs list
uv run bnf specs validate                # cross-refs every question back to a spec intention
uv run bnf specs render-prompt scratch_minidb

FINAL_AGENTS=(
  claude_code_opus_4_7_high
  claude_code_opus_4_7_low
  claude_code_sonnet_4_6_high
  claude_code_sonnet_4_6_low
  codex_gpt5_5_high
  codex_gpt5_5_low
  codex_gpt5_4_mini_high
  codex_gpt5_4_mini_low
  claude_code_mimo_v2_5_pro_high
  claude_code_mimo_v2_5_pro_low
  claude_code_mimo_v2_5_high
  claude_code_mimo_v2_5_low
)
AGENTS="$(IFS=,; echo "${FINAL_AGENTS[*]}")"

# Run the final-study scratch task set. See experiments/eandd_final_2026/SPEC.md
# for the frozen agent panel and trial contract before spending API budget.
uv run bnf run all \
  --tasks scratch_minidb,scratch_nanoweb \
  --builders "$AGENTS" \
  --finders "$AGENTS" \
  --build-trials 2 \
  --find-trials 3

# Dry-run the pipeline without invoking the real agents
BNF_DRY_RUN=1 uv run bnf run all \
  --tasks scratch_minidb \
  --builders "$AGENTS" \
  --finders "$AGENTS"

# Reproduce the reported release analysis and compile the paper
make reviewer-check-fast
make release-check
make paper-force
```

## Final-study analysis and figures

During a harness run, append-only `runs/records/*.json` files are the
local source of truth. The reviewer-facing artifact uses the sanitized
`runs_release/` tree as its source of truth. It includes release raw records,
generated build artifacts, canonical tables, and derived reports:

- `runs_release/records/*.json`
- `runs_release/artifacts/<build_run_id>/`
- `runs_release/tables/*.csv`
- `runs_release/reports/eandd_final/`

From a reported artifact checkout, regenerate the release tables and logical
paper reports directly from `runs_release/` with:

```bash
make release-check
```

`make paper-analysis` also reads `runs_release/` by default. For a private full
experiment checkout that should analyze unsanitized local evidence under
`runs/`, use `make local-paper-analysis`.
`runs_release/` is pruned to the final logical panel, spec-only and
question-only controls, and build-fidelity diagnostics. Pilot, edit-task,
legacy, and superseded records remain outside the reported artifact.

The canonical projection is:

- `build_runs.csv`: one row per build run.
- `find_runs.csv`: one row per finder invocation, keyed by task, builder,
  build trial, finder, finder trial, and per-run metrics.
- `question_answers.csv`: one row per answered multiple-choice question.
- `panel_membership.csv` and `experiments.json`: named panels such as
  `paper_final_scratch`, `high_effort_panel`, `low_effort_panel`, and
  `mimo_extension`. Primary paper panels require a status-ok build record, an
  existing artifact path, and a passing compile probe. The
  `artifact_present_diagnostic` panel retains all status-ok artifact-present
  builds, including compile-failed and empty artifacts summarized under
  `runs_release/reports/eandd_final/validity_stress/`.

Paper scripts depend on this table layer, so a new experiment appends raw
records first, prepares the release tree, and then regenerates the release
tables:

```bash
make prepare-release
make release-check
```

The reported artifact tables are:

- `runs_release/tables/build_runs.csv`
- `runs_release/tables/find_runs.csv`
- `runs_release/tables/question_answers.csv`
- `runs_release/tables/panel_membership.csv`
- `runs_release/tables/experiments.json`
- `runs_release/tables/MANIFEST.json`

The current NeurIPS E&D paper pipeline for the release tree is:

```bash
make paper-analysis   # final logical reports under runs_release/reports/eandd_final
make paper-figures    # figure PDFs/PNGs/SVGs under paper/neurips2026_eandd/figures
make paper            # compile the paper from current reports and figures
```

For the reported artifact, compile the PDF from checked-in reports and figures
with:

```bash
make paper-force
```

The retained paper-analysis scripts are:

- `scripts/analyze_eandd_final.py`
- `scripts/analyze_eandd_pivots.py`
- `scripts/analyze_eandd_within_finder_efficiency.py`
- `scripts/select_eandd_core_finders.py`
- `scripts/analyze_eandd_low_prior.py`
- `scripts/analyze_eandd_validity_stress.py`
- `scripts/analyze_eandd_calibration_uncertainty.py`
- `scripts/audit_finder_evidence_sample.py`

- `scripts/write_claim_evidence.py`

## Adding a new agent

Subclass `AgentAdapter` (or reuse `CodexAdapter` / `ClaudeCodeAdapter`),
register via `bnf.runners.registry.register`, and it becomes visible to
`bnf run all --builders ... --finders ...`.
